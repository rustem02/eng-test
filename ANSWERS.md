# Ответы на вопросы

Опыт опирается на реальные проекты: корпоративный портал **AQMOL** (FastAPI + React), экосистему **AllergoProba** / интеграционный сервис **macdent-integration-service**, плюс более мелкие продукты вроде дневника смен водителя.

---

## Аутентификация

### Где использовали не «толстый JWT в каждом запросе»

**1. AQMOL — JWT в HttpOnly-cookie + проверка прав из БД**  
В портале AQMOL access token кладётся в cookie `AQ_access_token`, а не гоняется как большой Bearer с кучей claims. В JWT по сути лежит `sub` (id пользователя) и срок жизни. На каждом запросе `get_current_user` декодирует токен и **заново поднимает пользователя и уровни доступа из PostgreSQL** (например, проверка уровня «АДМС» для админских операций).  

Это уже не классический «stateless JWT со всеми ролями внутри»: токен — скорее подписанная ссылка на сессию, а актуальные права всегда из БД. Отзыв/смена доступа ощущается быстрее, чем если бы роли жили только в payload до `exp`. Срок токена у нас сознательно длинный (до начала следующего месяца) — удобно для внутреннего портала, но как раз поэтому не тащим в JWT толстый набор permissions.

**2. macdent-integration-service — API keys и webhook secrets**  
Между MacDent и нашим шлюзом — `MACDENT_INBOUND_API_KEY` (`Authorization: Bearer` или `?api_key=`). Webhook от AllergoProba — отдельный `X-Webhook-Secret`. Исходящие вызовы в AllergoProba — JWT/API key сервиса (`FRONTEND_JWT` / `ALLERGOPROBA_API_KEY`).  

Здесь пользовательского JWT нет: это service-to-service. Гонять «человеческий» JWT с claims было бы лишним — нужен простой shared secret / ключ и идемпотентность на стороне Redis/Celery.

**3. AllergoProba**  
Клиентские/фронтовые сценарии ходят с JWT к API лаборатории; интеграционный слой поверх этого — ключи и секреты, как выше.

### Выбрал бы JWT, если мог выбирать?

**Да**, для:
- SPA/мобильных клиентов с отдельным API (как в этом тестовом репо);
- коротких access-токенов, когда revoke не критичен посекундно;
- внутренних сервисов, где в токене мало данных (как в AQMOL: почти только `sub`).

В AQMOL JWT **уже выбран** и я бы его оставил, но именно в связке «тонкий JWT в cookie + права из БД», а не как огромный self-contained ticket. Для macdent inbound я бы **не** менял API key на JWT пользователя — это другой threat model.

**Нет / другое** — если нужны мгновенный logout всех сессий, частая смена ACL и жёсткий контроль XSS: тогда server-side session в Redis (opaque cookie) или reference token. Для публичной clicker-игры из TASK JWT в localStorage/Bearer — нормальный pragmatic choice.

### Где бы заменил JWT на что-то другое

В **AQMOL**, если бы ужесточили требования по безопасности сессий (увольнение сотрудника должно сразу закрыть доступ ко всем вкладкам, без ожидания конца месяца), я бы ушёл на Redis-сессии или короткий access + refresh с blacklist, оставив cookie HttpOnly. Сейчас длинный JWT удобен продукту, но это компромисс.

В **macdent** JWT «как в Nest-примере» для inbound от MacDent я бы не выбирал — API key проще ротировать и мониторить по сервису-клиенту.

## Идентификация (UUID)

UUID удобны для публичных ссылок (`/round/:uuid` в этой игре) и генерации без координации. В практике проблемы были такие:

**1. AQMOL — смешанная модель**  
Основные сущности (пользователи, проекты, соглашения, отчёты) — integer/serial PK. UUID используем точечно, например имена файлов в images-сервисе (`uuid4().png`). Если бы UUID повесили как PK на все тяжёлые таблицы отчётов/соглашений с частыми JOIN и фильтрами — раздулись бы индексы и усложнилась бы отладка в SQL/тикетах («найди пользователя 8c3eed83-…»).

**2. macdent / AllergoProba — маппинг внешних ID**  
В интеграционном сервисе как раз болит не «UUID плох», а **разные пространства идентификаторов**: patient/application id AllergoProba ↔ id MacDent. Храним `patient_mapping`, `application_mapping` и т.д. Если бы обе стороны везде отдавали только random UUID без человекочитаемых/стабильных бизнес-ключей, саппорт и разбор конфликтов (`conflict_log`, `duplicate_log`) стали бы тяжелее. UUID как публичный id ок; как единственный способ понять «кто этот пациент» в переписке с клиникой — уже проблема.

**3. Write-heavy / синхронизация**  
При массовом синке и логах (`sync_log`, `integration_log`) random UUID как clustered PK на огромных append-only таблицах хуже sequential id по locality вставок. Для ~10 игроков в раунде игры это неважно; на интеграционных логах — уже да.

**Итог:** UUID как внешний/публичный идентификатор раунда — плюс. UUID «во всех таблицах как стандарт PK» без оглядки на объём, JOIN и поддержку — место, где я уже видел или ожидал боль (особенно рядом с маппингами AllergoProba↔MacDent и отчётными таблицами AQMOL).

## Организация кода

### Что реально помогало

**FastAPI `Depends` + слой DAO/сервисов (AQMOL)**  
Аналог Nest DI: роутер тонкий, `get_current_user` / `get_current_admin_user` централизуют authz, DAO изолируют SQLAlchemy. Когда чинил расчёт зарплат (командировки не учитывались) или добавлял кадровые операции (учебный отпуск), было важно, что правила лежат в сервисах/зависимостях, а не размазаны по хендлерам. Онбординг коллег проще: «сначала dependencies, потом dao, потом router».

**Клиент + сервисный слой в macdent**  
`AllergoprobaClient` (circuit breaker, retry, rate limit, метрики) отдельно от `MacDentAPIService` (кэш Redis, маппинг полей, создание заявок). Два HTTP-контура (`/api/macdent/v1` и `/macdent/v1`) с общей логикой — без этого дублировали бы преобразования под MacDent и «сырой» стиль AllergoProba. При уходе из проекта как раз это разделение позволило написать понятное руководство для следующих разработчиков.

**Модульность по доменам в AQMOL**  
`agreements`, `reports`, `hr`, `compensation`, `projects` — отдельные пакеты. На большой портальной кодовой базе это снижает конфликты в git и помогает искать баг («зарплата → compensation/salaries», «соглашения → agreements»).

### Что создавало сложности

**Размытая граница «куда класть бизнес-правило»**  
В AQMOL часть логики соглашений и отчётов со временем расползалась между router / dependencies / helpers. Появляются длинные функции и неочевидные side effects — DI сам по себе не спасает от god-модулей.

**Два API-контракта в macdent**  
Полезно для совместимости, но когнитивно тяжело: новый человек легко правит не тот роутер. Нужна дисциплина и документация (мы как раз её писали перед передачей проекта).

**Фоновые задачи (Celery) vs HTTP**  
Логика webhook/polling готовности результатов живёт и в push-эндпоинте, и в Beat-задаче. Без явного разделения легко починить только один путь. Это не Nest-специфика, но тот же класс проблем, что и «размазанный service layer».

Для Nest из этого репо: guards/modules мне близки по духу к FastAPI Depends + routers. Я бы не тащил Nest ради Nest в крошечный сервис, но для игры с auth + games модулями — ок.

## Реактивность (React)

### Когда мешала

**AQMOL-портал (React + Ant Design / MUI)**  
Тяжёлые экраны: оргструктура, графики, таблицы отчётов, формы соглашений. Реактивность провоцирует каскадные ре-рендеры: поменяли фильтр — перерисовалось полдерева. Особенно неприятно, когда рядом ещё и локальный state формы + данные с API + derived «можно ли сохранить». Баги вида «после правки коэффициентов/этажности UI показывает старое, пока не перезагрузишь» — классика рассинхрона нескольких источников правды.

**Интеграционные админки / ожидание фоновых процессов**  
Статус заявки в AllergoProba меняется асинхронно (Celery, webhook). Если просто «положи в state и забудь», React честно рисует устаревшее. Нужен polling/refetch, а не только реактивная модель.

**Таймеры на странице раунда (этот TASK)**  
`setState` каждую секунду на всю страницу — реактивность работает, но легко утащить за собой лишний render гуся и блоков статистики. Таймер лучше изолировать.

### Другой принцип рендера

Часть внутренних инструментов и отчётов в экосистеме ближе к «сервер отдал HTML/данные → минимум магии на клиенте» (экспорт Excel, sqladmin в AQMOL). Там предсказуемее: нет гонки optimistic UI. Для богатых форм портала React всё же выигрывает по скорости итераций.

### Что бесит в React конкретно

1. **Stale closures / зависимости `useEffect`** — легко словить баг после навигации между сущностями (в портале — между проектами/соглашениями; здесь — между `round/:uuid`).
2. **Несколько источников правды** — token в localStorage, user из decode JWT, список с сервера, локальные фильтры.
3. **Асинхронные гонки** — быстрый клик/переход: ответ старого запроса перетирает новый state (та же история, что с устаревшим score при тапах).
4. **Оптимистичный UI vs серверная истина** — в кликере и в статусах заявок AllergoProba сервер главнее; React сам это не навязывает.

## Рабочий процесс

Ориентир — последние годы: AQMOL (баги зарплат/кадров/соглашений), macdent↔AllergoProba (интеграция, метрики, деплой), плюс мелкие pet/test задания.

### Рабочий день

Утро: глянуть, что горит (прод/тест AllergoProba, тикеты по порталу), короткий синк если есть. Дальше один основной фокус: либо баг с воспроизведением (командировки в зарплате, фидбек по интеграции из `new_bugs.md`), либо фича целиком (учебный отпуск в кадровых операциях, Grafana-метрики на общий стек). Вперемешку — ревью, правки по API, деплой-скрипты (`run.sh`, restart на сервере). Вечером стараюсь оставить зелёный прогон или понятный черновик PR / список «что проверено на стенде».

### Фокус на одной задаче

Комфортно **1.5–2 часа** подряд, потом короткий перерыв. Крупное дроблю: сначала контракт/SQL, потом API, потом UI, потом краевые случаи. Интеграции (macdent) почти всегда режу на «happy path с одним пациентом» → маппинги → webhook/Celery → метрики.

### Когда считаю, что качественно

- Сценарий из бага/ТЗ воспроизведён и закрыт (не «вроде поправили»).
- Есть проверка на стенде (тест AllergoProba / локальный AQMOL), не только «скомпилилось».
- Учтены соседние пути (push webhook **и** polling Celery; роль admin **и** обычный user).
- Для передачи проекта — документация или хотя бы комментарий в PR, почему так (как с руководством по macdent).
- Не ломает основной поток: создание соглашения, получение пациентов, логин на портал.

### Если жду сборку / ответ / ревью

- Дописать тесты или чеклист ручной проверки.
- Почистить мелочь (env.example без секретов, скрипт рестарта).
- Параллельно мелкий тикет, если ожидание > получаса; если 2–5 минут — не переключаюсь.
- Иногда — разобрать метрики/логи Grafana, пока коллеги смотрят фидбек.

### «Достаточно за день»

Сдвинулся риск: баг воспроизводим и закрыт, или интеграция на шаг ближе к прод (ключ, URL, один стабильный эндпоинт), или фича в PR с понятным описанием. Не меряю день числом коммитов. Если весь день ушёл на расследование — фиксирую findings в тикете/доке: это тоже результат, иначе кажется, что день пустой.
